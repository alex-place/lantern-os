- **Sign-in works again on any PORT-launched local server, and `LANTERN_ADMIN_IDS` can finally elevate an email/password account** — two auth-path bugs found during the 2026-07-27 user-flow pass:
  - **#3010:** the session cookie was marked `Secure` whenever `PORT` was set (`server.js`), but a launcher that injects `PORT` on plain-http localhost (the preview tool, autostart) is not https — so `express-session` saved the session yet silently dropped `Set-Cookie`, and every sign-in (test-role picker, email+password, OAuth) returned `200 ok` while the browser stayed guest with no error anywhere. Cookie `secure` is now `"auto"`, which (with `proxy:true`) tracks the real connection: `Secure` behind Railway's TLS via `X-Forwarded-Proto`, sent non-`Secure` on local http so login persists. Verified live: a PORT-set http `test-login` now returns `Set-Cookie` and the next `/api/auth/session` reads the authed role.
  - **#3087:** the local (email/password) login path never ran the `profileHasAdminOverride` elevation the OAuth path does, so even a correctly-qualified `LANTERN_ADMIN_IDS=local:you@email.com` silently stayed `guest` — on a Google-less deploy there was no working route to admin. Local login now applies the same override (elevate-only). Plus a startup warning when an admin-id entry is bare (read as a Google id — surprising if you meant your local email) or names a provider no login path checks.
